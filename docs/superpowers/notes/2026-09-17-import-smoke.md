# 阶段 3 设备导入实机实测（2026-09-17）

设备：Apple iPhone（USB 直连 WPD）。目标库：`D:\图片\Pictures\iPhone`。
方法：先用界面导入（`LIVEPORTER_IMPORT_LOG=1`），后改用**无界面实机测试**
`cargo test -p liveporter real_device_transfer_smoke -- --ignored --nocapture`（`LPM_SMOKE_N` 控制文件数）。

## 一、最重要的结论：对象句柄必须用持久 ID 重解析

**症状（严重）：** 早期实现直接拿枚举得到的对象 ID 去 `GetStream`，表面"成功"、无报错，
但**写入的内容是错的**。实测 20 个文件，全部错位 2 个对象：请求 `IMG_1716.MOV` 写下的却是
`IMG_1717.MOV` 的内容，前两个请求甚至只拿到 195 字节的 **MTP ObjectInfo 元数据**
（含 `202609_a`、`20260901T000000.0` 等字样），根本不是照片/视频。

**根因：** iOS 的 WPD 对象句柄是**易失**的——在枚举与属性读取之后会失效，继续拿去取流会
命中**错误对象**。这正是设计 §12 警告的「iPhone 走 WPD 的怪癖」。

**修复：** 枚举时一并读取 `WPD_OBJECT_PERSISTENT_UNIQUE_ID`（稳定），传输前用
`IPortableDeviceContent::GetObjectIDsFromPersistentUniqueIDs` 把它重解析成**新鲜句柄**再取流。

**修复后验证：**
- 20/20 成功、`wrong_content=0`、每个文件 `got == reported` 大小完全一致。
- 扩大到 **60/60 成功、`fail=0`、`wrong_content=0`**（365.8 MB），确认修复不是偶然。

> 教训：**"没报错"不等于"内容对"。** 传输类功能必须校验字节数（乃至内容头），不能只看是否有异常。

## 二、残留的间歇性失败：用重试兜住

在**干净会话**下，修复句柄后仍偶发 `GetStream` 失败（错误 `0x80042007`，多为 MOV，即实况的
第二个文件），以及 `0x8007001E`（`ERROR_READ_FAULT`）。表现为部分文件耗时约 10s——
即第一次尝试失败后重试成功。

对策（已实现）：
1. `GetStream` 失败时**退避重试**（5 次，150ms×attempt 递增）。
2. 每次成功读取后**按序显式释放** `IStream` 与 `IPortableDeviceResources`，并留 250ms 间隔。
3. **不要**在成功路径调用 `resources.Cancel()`（早期试过，无效且可能干扰会话；已移除）。

## 三、会话会被强杀进程卡死

多次用 `Stop-Process` 强杀应用后，设备侧 WPD 会话卡住：连**枚举都过不去**（无界面测试
卡死 20 分钟无输出），并表现为每次 `GetStream` 阻塞约 30s 才失败。**只能物理拔插数据线恢复**，
拔插后还需在手机上重新解锁并「信任此电脑」。

> 这对产品意味着：真实的"断电/拔线"场景需要能恢复。目前重插后可用；后续应加入
> "会话失效时提示用户重插"的引导。

## 四、传输速率

修复后的无界面测试（60 个文件）：`bytes=365,799,050` / `274.75s` ≈ **1.33 MB/s**（与界面导入的
1.2~1.5 MB/s 同量级）。首文件瞬时可达约 8.9 MB/s。**低于设计预期 5~15 MB/s。**
未验证并发流能否提速（设计默认并发 1）。

## 五、结论

- 导入管道、状态机、断点续传、`originals/<device>/<year>/` 组织、`.part` 写名后改名：**成立**。
- **正确性**：修复持久 ID 重解析后成立（有字节数校验）。
- **可靠性**：干净会话下靠重试兜住；会话卡死需重插恢复。
- **速率**：约 1 MB/s，明显偏低，待优化。
- **未做**：并发流实测、速率瓶颈定位。

## 六、对早先入库数据的警告

在修复之前，界面导入把 **66 个条目**标记为 `copied` 写入了 `D:\图片\Pictures\iPhone`，
**这些文件内容很可能是错位的、无效的**。该库应视为脏数据，需删除后重导（`.lpm/index.db`
里的这 66 行也将因 `existing_sizes` 被跳过，必须先清掉）。
