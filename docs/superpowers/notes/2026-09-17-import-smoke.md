# 阶段 3 设备导入实机实测（2026-09-17）

设备：Apple iPhone（USB 直连 WPD），库：`D:\图片\Pictures\iPhone`。
方法：`npm run tauri dev` 并设 `LIVEPORTER_IMPORT_LOG=1`，从界面点「从 iPhone 导入」。

## 结论摘要

| 项 | 结果 |
|---|---|
| 设备枚举 / 增量比对 | 正常（任务数约 885~1038，取决于已导入数） |
| 状态机（pending→copied / failed） | 正常，DB 可见 |
| 断点续传（已 copied 跳过、pending/failed 重试） | 正常 |
| 中文/实况配对写入 `originals/<device>/<year>/` | 正常 |
| `.part` 写临时名再改名 | 正常 |
| **静态图（JPG）传输** | **基本成功** |
| **视频（MOV，实况的动态部分）传输** | **间歇失败，未完全解决** |
| 传输速率 | 首文件约 8.9 MB/s，随后稳定在 **约 1.2~1.5 MB/s**（设计经验值 5~15 MB/s，实测偏低） |

## 失败错误的原文（存在 `asset.error`）

```
IMG_0284.MOV: GetStream 失败: 0x80042007
IMG_0271.JPG: GetStream 失败: 系统无法从指定的设备上读取。 (0x8007001E)
```

- `0x80042007`：设备侧 ITF facility 错误（低字 `0x2007` 像 MTP 响应码），**绝大多数出现在 `.MOV`**，即每个实况的**第二个**文件。
- `0x8007001E`：Win32 `ERROR_READ_FAULT`（"系统无法从指定的设备上读取"），偶发。

## 调查过程与两处尝试

1. **先怀疑 `IPortableDeviceResources::Cancel()`。** 原实现在每个文件下载成功后调用 `Cancel()`；因 `content.Transfer()` 很可能返回同一个内部对象，怀疑 Cancel 打断了设备会话。
   **去掉 `Cancel()` 后失败率没有改善**（仍然约 70%）。→ 排除该假设，但**保留去掉 Cancel** 的改动（成功路径不应调 Cancel）。
2. **退避重试 `GetStream`（5 次，150ms×attempt 递增）。** 加入后：
   - 有一次运行**连续 18 个资产零失败**，速率正常。
   - 另一次运行在约 7 个资产后**失败重现**（每 1~2s 失败一个，说明重试被很快耗尽）。
   → 重试**显著缓解但不能根治**。失败是**间歇性、与设备状态相关**的。

**当前最可信的假设：** iOS 的 PTP 会话在上一个流尚未在设备侧完全释放前，新的 `GetStream`（尤其对视频对象）会失败；这种"未释放窗口"与设备内部时序有关，因此表现出间歇性。

## 未完成 / 下一步候选方案（供后续计划）

1. **按对象重解析句柄**：枚举时一并读取 `WPD_OBJECT_PERSISTENT_UNIQUE_ID`，传输前用
   `IPortableDeviceContent::GetObjectIDsFromPersistentUniqueIDs` 换取新鲜对象 ID，规避 iOS 句柄失效。
2. **在实况的两个文件之间强制间隔/释放**：读完静态图后显式释放流与 resources，并等待一小段时间（如 200~500ms）再取视频；或对失败对象在"重新打开设备会话"后重试。
3. **调整读取块大小**：目前用设备建议值 clamp 到 [64KB, 1MB]，可实测更大/更小对速率与稳定性的影响。
4. **传输速率偏低（~1.2MB/s）**：需确认瓶颈（是设备端节流、还是每文件的会话开销）。整机 ~11GB 在 1.2MB/s 下要 ~2.5 小时。

## 判定

按计划 4 的完成判据，**Task 8 未完全通过**：导入管道、状态机、断点续传、写盘命名都成立，但**视频传输的可靠性不达标**（间歇 `0x80042007`）。

这是一次**有价值的负面结果**：设计文档 §12 把"iPhone 走 WPD 的怪癖"列为高风险，实测证实了这一点，并锁定了问题范围为「视频对象的流获取时序」而非「通道不可用」。通道本身可用——大量静态图与部分视频已成功落地。
