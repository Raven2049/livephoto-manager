# 阶段 3 设备导入实机实测（2026-09-17）

设备：Apple iPhone（USB 直连 WPD）。目标库：`D:\图片\Pictures\iPhone`。
方法：先用界面导入（`LIVEPORTER_IMPORT_LOG=1`），后改用**无界面实机测试**
`cargo test -p liveporter real_device_transfer_smoke -- --ignored --nocapture`（`LPM_SMOKE_N` 控制文件数）。

## 一、最重要的结论：对象句柄必须用持久 ID 重解析

**症状（严重）：** 早期实现直接拿枚举得到的对象 ID 去 `GetStream`，表面"成功"、无报错，
但**写入的内容是错的**。实测 20 个文件，全部错位 2 个对象：请求 `IMG_1716.MOV` 写下的却是
`IMG_1717.MOV` 的内容，前两个请求甚至只拿到 195 字节的 **MTP ObjectInfo 元数据**
（含 `202609_a`、`20260901T000000.0` 等字样），根本不是照片/视频。

**根因：** iOS 的 WPD 对象句柄是**易失**的——在枚举与属性读取之后会失效，继续拿去取流会
命中**错误对象**。这正是设计 §12 警告的「iPhone 走 WPD 的怪癖」。

**修复：** 枚举时一并读取 `WPD_OBJECT_PERSISTENT_UNIQUE_ID`（稳定），传输前用
`IPortableDeviceContent::GetObjectIDsFromPersistentUniqueIDs` 把它重解析成**新鲜句柄**再取流。

**修复后验证：**
- 20/20 成功、`wrong_content=0`、每个文件 `got == reported` 大小完全一致。
- 扩大到 **60/60 成功、`fail=0`、`wrong_content=0`**（365.8 MB），确认修复不是偶然。

> 教训：**"没报错"不等于"内容对"。** 传输类功能必须校验字节数（乃至内容头），不能只看是否有异常。

## 二、残留的间歇性失败：用重试兜住

在**干净会话**下，修复句柄后仍偶发 `GetStream` 失败（错误 `0x80042007`，多为 MOV，即实况的
第二个文件），以及 `0x8007001E`（`ERROR_READ_FAULT`）。表现为部分文件耗时约 10s——
即第一次尝试失败后重试成功。

对策（已实现）：
1. `GetStream` 失败时**退避重试**（5 次，150ms×attempt 递增）。
2. 每次成功读取后**按序显式释放** `IStream` 与 `IPortableDeviceResources`，并留 250ms 间隔。
3. **不要**在成功路径调用 `resources.Cancel()`（早期试过，无效且可能干扰会话；已移除）。

## 三、会话会被强杀进程卡死

多次用 `Stop-Process` 强杀应用后，设备侧 WPD 会话卡住：连**枚举都过不去**（无界面测试
卡死 20 分钟无输出），并表现为每次 `GetStream` 阻塞约 30s 才失败。**只能物理拔插数据线恢复**，
拔插后还需在手机上重新解锁并「信任此电脑」。

> 这对产品意味着：真实的"断电/拔线"场景需要能恢复。目前重插后可用；后续应加入
> "会话失效时提示用户重插"的引导。

## 四、传输速率

修复后的无界面测试（60 个文件）：`bytes=365,799,050` / `274.75s` ≈ **1.33 MB/s**（与界面导入的
1.2~1.5 MB/s 同量级）。首文件瞬时可达约 8.9 MB/s。**低于设计预期 5~15 MB/s。**
未验证并发流能否提速（设计默认并发 1）。

## 五、结论

- 导入管道、状态机、断点续传、`originals/<device>/<year>/` 组织、`.part` 写名后改名：**成立**。
- **正确性**：修复持久 ID 重解析后成立（有字节数校验）。
- **可靠性**：干净会话下靠重试兜住；会话卡死需重插恢复。
- **速率**：约 1 MB/s，明显偏低，待优化。
- **未做**：并发流实测、速率瓶颈定位。

## 七、并发流实验（回答设计附录 B 第 3 项）

新增无界面实验 `real_device_parallel_smoke`：`LPM_PARALLEL` 个线程，各自 `ComGuard` + `Open`
设备会话，各下一部分文件（先单线程枚举出清单，清单是纯数据可跨线程）。

| 并发数 | 成功/失败 | 吞吐 | 备注 |
|---|---|---|---|
| 1（顺序，N=20） | 20 / 0 | **1.65 MB/s** | 基线 |
| 2（N=20） | 18 / 2 | 2.09 MB/s | 失败为 `0x800700AA` ERROR_BUSY（资源在使用中） |
| 4（N=40） | 27 / 13 | 1.42 MB/s | 失败率 **33%**，全是 ERROR_BUSY |

**结论：并发流没有实质收益，反而引入争用错误。**
- 设备（iOS PTP）在并发取流时会返回 `ERROR_BUSY`，说明底层事务是**串行**的。
- 2 线程看似 +27%，但伴随 10% 失败，且很可能是运行间波动（顺序版本身在 1.0~1.65 MB/s 波动）。
- 4 线程吞吐反而低于顺序版，失败率 33%。
- **建议维持设计默认：并发 = 1。** 吞吐瓶颈在设备端每文件延迟（部分文件有约 10s 的停滞），
  不是"没并发"。

> 这也印证了设计 §2.2 的判断：能优化的是管道编排，不是单次传输速率。

## 九、低速定位：瓶颈是"首次访问"的设备端延迟

用分阶段计时（`real_device_timing_smoke`）拆开每个文件的耗时，再用"同一文件连下两次"
（`real_device_repeat_smoke`）对比：

**阶段拆解：** 解析持久 ID ~0.3ms、`GetStream` ~0.01s（且首次即成功，无重试），
**时间全在读取循环**。所以停滞既不是句柄解析、也不是取流握手、也不是收尾那次 Read
（把循环改成"读够 `size` 就停"后停滞依旧）。

**连下两次的对比（同一批 MOV）：**

| 文件 | 第一次读取 | 第二次读取 |
|---|---|---|
| IMG_1716.MOV | 9.89s（0.63 MB/s） | **0.16s（37.6 MB/s）** |
| IMG_1715.MOV | 0.49s | 0.17s |
| IMG_1713.MOV | 0.67s | 0.23s |
| IMG_1712.MOV | 9.96s（1.01 MB/s） | **0.26s（38.4 MB/s）** |

**结论：**
- **首次读取约 0.5~10s（约 1 MB/s 或更慢），第二次读取约 38 MB/s（接近 USB 速率）。**
  即瓶颈是**每个文件"第一次被访问"时的设备端开销**，数据读完一次后就已缓存。
- 这不取决于缓冲大小（设备建议 256 KiB，已采用）、不取决于并发（已实测无收益）、
  与我们的代码无关。
- **慢的文件在不同次运行中并不固定**（一次是 IMG_1713/1712/1711/1710/1709，另一次是
  IMG_1716/1712），说明这是**状态相关**的缓存行为，而不是"某些文件特殊"。

> **已排除 iCloud `优化 iPhone 储存空间`：用户确认手机上该设置未开启。** 因此首访延迟不是
> "去云端取回"，而是设备/驱动侧的**首次访问准备或缓存**（可能是 iOS 照片库把原件物化成
> 可传输文件、解密、或驱动层预取后缓存）。**具体机制从 Windows 主机侧无法区分**，未再深挖。

**产品含义：**
1. 无法通过并发/缓冲优化首访延迟；整机导入的耗时下限 ≈ Σ(每个文件的首访延迟)。
2. 若后续要改善，可考虑的方向是"减少首访次数"（每个文件只读一次——本来如此）与
   "让设备把文件预热"，但没有可验证的抓手。
3. 设计 §6.4 的 iCloud 检测仍然是待办，但**与本低速问题无关**，不应再混为一谈。
