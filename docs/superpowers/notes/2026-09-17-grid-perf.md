- 开发机、dev 构建、数据源为**本地普通图片目录**（非 iPhone）
- 相关代码：`src/components/PhotoGrid.vue`、`src-tauri/src/protocol.rs`、`src-tauri/src/lib.rs`

## 首轮问题与修复

### 问题 1：拖动滚动条明显卡顿

**现象**：滚轮流畅，但拖动滚动条卡。

**根因**：拖动滚动条会一次跳过大量行，每一帧都挂载带真实 `src` 的 `<img>`，导致**沿途每一屏的图片都真的发起了请求**（全分辨率原图，几 MB/张）。滚轮是逐行推进，图片慢慢加载，所以不卡。

**修复**（`PhotoGrid.vue`）：

1. **滚动停稳 150ms 后才给新瓦片挂 `src`**；滚动途中用 1x1 透明 GIF 占位（透出深色背景，即肉眼看到的"黑块"）。
2. 用 `loaded: Set<number>` 记录"曾加载过"的 index：已加载的瓦片再回到视口时**立即**用真实 URL，不回退成占位图、不重复加载。
3. `scroll` 回调用 `requestAnimationFrame` 节流，一帧最多一次重渲染。
4. 去掉 `.tile` 的 `will-change: transform`（大量瓦片各自提升合成层是反模式）。
5. 协议处理从 `std::thread::spawn`（每请求裸建线程）改为 `tauri::async_runtime::spawn_blocking`（受控阻塞线程池）。

### 问题 2：回划时重复读盘

**根因**：`lpm://` 响应没有缓存头，浏览器不认为可缓存，回划会重新请求并重新解码。

**修复**（`protocol.rs`）：加 `ETag`（`修改时间纳秒 + 文件大小`）+ `Cache-Control: no-cache`，并处理 `If-None-Match` → 返回 `304 Not Modified`（不带文件内容）。回划时浏览器校验命中 304，不再读盘/解码。

### 问题 3：`npm run tauri dev` 偶发 EBUSY 崩溃

**根因**：`src-tauri` 成为 workspace 成员后，Rust 产物落在**仓库根** `target/`，而 `vite.config.ts` 只忽略了 `**/src-tauri/**`。cargo 重编译写 DLL 时 Vite 监视到并抛 `EBUSY`。

**修复**：`vite.config.ts` 的 `watch.ignored` 增加 `"**/target/**"`。

## 结论

- 设计文档 §8 的三条硬性决定成立：自写虚拟滚动 + 固定瓦片 + 自定义协议，在**万级以内的本地图片**上表现良好。
- 「全分辨率原图直接上网格」在**修复后**可用，但仍有优化空间。设计 §7.4 规划的 **512px 缩略图（计划 3，依赖 ffmpeg）** 到位后，内存与解码压力会显著下降，届时需复测本表。
- 协议已具备 Range + ETag，满足设计 §8.1 决定 3（支持拖动进度、天然吃 HTTP 缓存）的基础要求。
