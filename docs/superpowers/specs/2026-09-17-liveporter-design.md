# LivePorter 设计文档

> 把 iPhone 上的实况照片（Live Photos）连同其动态视频一起、批量地、配对无损地搬到 Windows 硬盘上，并提供一个像 iOS 相册一样的浏览界面。

- 日期：2026-09-17
- 状态：待审阅
- 仓库：`git@github.com:Raven2049/livephoto-manager.git`

---

## 1. 目标与非目标

### 目标

1. **配对无损搬运**：实况照片在 iPhone 上由两个文件组成（静态图 `HEIC`/`JPG` + 同名短视频 `MOV`）。工具必须把两者一起取出、保持配对关系、不转码不损失。
2. **一口气批量**：插上手机就能把整机相册增量同步到本地，中途可中断、可续传。
3. **像 iOS 相册的浏览体验**：网格视图、Ctrl+滚轮缩放、鼠标悬停即播放动态。
4. **完全开源、免费**：面向互联网分发，任何人可用。

### 非目标（v1 明确不做）

- 收藏 / 标星
- 自定义相册 / 标签
- 删除时同步删除手机上的文件（双向删除）
- 把本地照片传回 iPhone
- 导出时转成 JPG / MP4（导出即原样拷贝配对文件）
- macOS / Linux 支持（macOS 有系统自带方案，Linux 无 iPhone 生态，本工具专攻 Windows 这个空白）

## 2. 技术前提与约束

### 2.1 实况照片的文件结构

一张实况照片 = 两个文件，共享同一个 `ContentIdentifier`（UUID）：

- 静态图：`IMG_1234.HEIC`（或 `.JPG`）
- 动态视频：`IMG_1234.MOV`（约 1.5~3 秒，默认 HEVC/H.265 编码）

`ContentIdentifier` 是 iOS 自己用来配对的权威依据：静态图里存在 EXIF 的 Apple MakerNote，视频里存在 QuickTime metadata atom。

### 2.2 数据通道：Windows 上只有一条路

Windows 访问 iPhone 相册**只能**通过 WPD（Windows Portable Devices）COM 接口，底层是 iOS 的 PTP 实现。无论用 Rust、C#、Python 还是 PowerShell，调用的都是同一套 Windows 驱动栈，**传输速度由设备端决定，与实现语言无关**（经验值 5~15 MB/s）。

不存在"换语言就能更快"的空间。能优化的是管道编排，不是单次传输速率。

### 2.3 两个必须先实测确认的未知项

| 未知项 | 影响 | 验证方式 |
|---|---|---|
| MTP 是否稳定暴露实况照片的 `.MOV` 文件 | 决定整个方案可行性 | ✅ **已实测：成立**（见 §2.4） |
| 如何可靠检测"优化 iPhone 储存空间"已开启且原件不在手机 | 决定能否防住"导入一堆糊图" | 仍未验证，见 §6.4 |

有第三方实测报告称通过资源管理器/MTP 拷贝时同名 `.MOV` 会被一并拷出，但这**不构成结论**，必须用自己的设备验证。

### 2.4 阶段 0 实测结论（2026-09-17，开发机）

用一次性只读 PowerShell 脚本（Windows Shell COM，**非** WPD 直调）枚举了一台 iPhone 的 MTP 内容：

- **结论：GO。** `.MOV` 动态部分确实通过 MTP 暴露，且能与静态图按主名配对。
- 计数：文件总数 193（`.mov` 96、`.jpg` 93、`.aae` 4）；同名「静态图 + MOV」配对 **93** 对，孤立 MOV 3，仅静态 0。
- 设备：`Apple iPhone`（USB `VID_05AC&PID_12A8`），存储卷 `Internal Storage`（约 256 GB）。

实测中发现、与设计假设不符的点（后续计划必须据此调整）：

1. **顶层没有 `DCIM` 目录。** `Internal Storage` 下直接是 `202504_a`，文件全在其下。设计 §4 与计划 Task 9 的白名单「只进 DCIM」需放宽为「递归整卷、按扩展名过滤」。
2. **`FolderItem.Name` 不含扩展名**（Windows 隐藏已知扩展名），同名 `.MOV` 与 `.JPG` 的 `Name` 完全相同。取真实文件名必须用扩展属性 `System.FileName`（或 `System.FileExtension`），不能靠 `Name` 截取。
3. **本机静态图是 `.JPG`，没有 `.HEIC`。** 该设备可能设成了「兼容性最佳」。HEIC 路径在本设备上未得到验证。
4. 存在 `.AAE` 伴生文件与 `IMG_E….`/`IMG_O….`（编辑版/原版）变体，配对逻辑需把它们归入 `Other`、并按 stem 正确区分。
5. `FolderItem.Size` 返回 0，字节数须读扩展属性 `System.Size`。

> ⚠️ 本次用的是 Shell COM 通道，**不是**最终实现要走的 WPD COM 直调。因此 Task 10 的 Rust WPD 探测仍然必须做，并与本次计数（193）交叉核对——两条独立通道给出一致结果，才能确认 WPD 层实现正确。

### 2.5 WPD 直调实测结论（2026-09-17，`crates/probe`）

计划 1 的 Rust 只读探测程序（直接用 `windows` crate 调 WPD COM，`IPortableDeviceManager` / `IPortableDevice` / `IPortableDeviceContent` / `IPortableDeviceProperties`）：

- **结论：GO，且与 Shell 通道交叉核对。**
- WPD 计数：文件总数 **1987**（`.mov` 991、`.jpg` 971、`.png` 15、`.aae` 8、`.gif` 2）；同名「静态图 + MOV」配对 **942** 对，仅静态 46，仅视频 49。
- 设备信息：`Apple iPhone` / 型号 `Apple iPhone` / 序列号（打码）`******4RV0`。
- 存储：`Internal Storage`，容量约 256 GB，可用约 80.5 GB（`WPD_STORAGE_CAPACITY` / `WPD_STORAGE_FREE_SPACE_IN_BYTES`）。

**交叉核对结果：WPD（1987）远多于 Shell（193）。** 这不是 bug——资源管理器对 iPhone 的 MTP 视图只暴露了 `Internal Storage\202504_a` 一个目录，而 WPD 直调能看到整机全部相册/目录。结论：**必须走 WPD 直调，不能依赖资源管理器视图来清点设备内容**（设计 §2.2 的判断得到实测支持）。

本次还确认了几处实现细节（后续计划沿用）：

1. **`PWSTR` 取字符串必须处理结尾 NUL。** `pwstr.as_wide()` 返回的切片不含终止符；把它当 `PCWSTR` 直接传给 COM（如 `IPortableDevice::Open`）会读到越界内存并返回 `E_POINTER (0x80004003)`。凡自行构造宽字符串，必须补 `0`。
2. **`IPortableDevice::Open` 的 PnP 设备 ID 取自 `IPortableDeviceManager::GetDevices`**，且系统上可能同时存在多个 WPD 设备（实测本机 `GetDevices` 返回 2 个，其中一个是把本机磁盘映射成 WPD 的设备）。必须按 `GetDeviceFriendlyName` 过滤出 iPhone（含 `iPhone`/`Apple`）再 `Open`，否则会枚举到本机磁盘。
3. `windows` 0.58 已从 SDK 自动生成并导出全部所需 `WPD_*` 常量，**无需手工抄录头文件**。但 `PROPERTYKEY` 类型位于 `Win32::UI::Shell::PropertiesSystem`（不是 `Win32::Foundation`），需启用 feature `Win32_UI_Shell_PropertiesSystem`。
4. `IPortableDevice::Open` 的 client info 传 `None` 亦可，但实测显式创建 `CLSID_PortableDeviceValues` 更稳。
5. 未读取任何文件字节：本阶段只读取元数据（名字/大小/时间/内容类型），**未下载任何照片**，符合设计 §12 与计划「只读」要求。因此**传输速率与并发流数量的关系仍未实测**（附录 B 第 3 项、§12 对应风险项）——该数据只能在实际落地文件传输时采集，留待计划 3（导入管道）。
6. 系统上可能存在对 `Open` 会挂起的"幻影"WPD 设备（实测：拔掉 iPhone 后 `GetDevices` 仍返回 1 个把本机磁盘映射成 WPD 的设备，对其 `Open` 无限期阻塞）。实现必须按友好名只打开 Apple/iPhone 设备，无匹配即当作无设备退出。

## 3. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 外壳 | **Tauri 2.x** | 内存占用约为 Electron 的 1/3；WebView2 在 Win10/11 上自带，不必打包浏览器 |
| 核心 | **Rust** | 无 GC；WPD COM 可用官方 `windows` crate 绑定；ffmpeg 调度和 SQLite 都有成熟 crate |
| 前端 | **Vue 3 + TypeScript + Vite** | Tauri 默认组合；构建产物小 |
| 索引 | **SQLite**（`rusqlite`，bundled） | 万级以上条目的分页查询、增量比对需要真正的数据库 |
| 媒体处理 | **ffmpeg**（裁剪版静态构建，子进程调用） | 唯一能同时解 HEIC、解 HEVC、编 H.264 的成熟方案 |

### 为什么不用 Electron

Electron 空闲即占 150~250 MB，UI 能力与 WebView2 同级（都是 Chromium 系）。既然明确以"性能 + 轻量"为目标，Electron 是三个候选里最差的一个。

### 为什么不依赖 WebView2 的 HEVC 解码

Chromium 解不了 HEIC 图片；HEVC 视频仅在用户额外安装了微软商店的 HEVC 扩展时才可能通过系统解码器播放。**不能指望终端用户具备这个条件**，所以统一由 ffmpeg 生成 H.264 预览片，保证 100% 可播。

## 4. 库的目录结构

用户指定一个硬盘目录，该目录**就是**库。app 不维护第二份内部副本。

```
D:\LivePhotos\
├── originals\
│   └── iPhone15Pro-3F9A2C\            ← 每台设备一个目录
│       ├── 2024\
│       │   ├── IMG_1234.HEIC
│       │   ├── IMG_1234.MOV           ← 与静态图同目录、同主名，配对不分离
│       │   └── IMG_1235.MOV           ← 纯视频
│       └── 2025\
├── thumbs\
│   └── <hash>.webp                    512px WebP 缩略图
├── previews\
│   └── <hash>.mp4                     480p H.264 预览片（按需生成）
└── .lpm\
    └── index.db                       SQLite 索引（隐藏目录）
```

### 设计要点

- **设备目录名固定为 `<型号>-<序列号后6位>`**，例如 `iPhone15Pro-3F9A2C`。不用设备名（用户可改、可能含非法字符），不用纯序列号（太长不便浏览）。
- **年份取拍摄时间，不取导入时间**。
- `thumbs/` 和 `previews/` 用内容 hash 命名，避开不同设备/年份的文件名撞车。
- **`.lpm/` 可随时删除**：删掉只是丢失索引和缓存，原始文件完好，重新扫描可重建。这是"库目录即数据"这一决策的核心保证。

## 5. 数据模型

### 5.1 逻辑条目

一个 `asset` 表示"一个逻辑条目"，而不是一个文件。实况照片的两个文件挂在同一条记录上。

### 5.2 表结构（设计级，非最终 migration）

```sql
CREATE TABLE device (
  id            INTEGER PRIMARY KEY,
  serial        TEXT NOT NULL UNIQUE,   -- 设备序列号，稳定标识
  model         TEXT NOT NULL,          -- 型号标识
  display_name  TEXT,                   -- iPhone 上的设备名，仅用于界面显示
  folder_name   TEXT NOT NULL,          -- originals/ 下的目录名
  last_seen_at  INTEGER
);

CREATE TABLE asset (
  id            INTEGER PRIMARY KEY,
  device_id     INTEGER NOT NULL REFERENCES device(id),

  kind          INTEGER NOT NULL,       -- 1=photo  2=video  3=live
  base_name     TEXT NOT NULL,          -- 原文件名主名，如 IMG_1234
  taken_at      INTEGER NOT NULL,       -- 拍摄时间（epoch 秒），来自设备元数据

  still_path    TEXT,                   -- 相对库根路径；video-only 时为 NULL
  still_ext     TEXT,                   -- heic / jpg
  still_size    INTEGER,

  movie_path    TEXT,                   -- photo-only 时为 NULL
  movie_ext     TEXT,                   -- mov / mp4
  movie_size    INTEGER,

  content_id    TEXT,                   -- 从文件内部读到的 ContentIdentifier
  integrity     INTEGER NOT NULL DEFAULT 0,
                -- 0=正常  1=UUID 校验不一致  2=残缺实况（有 UUID 但缺伴生文件）
                -- 3=仅静态（无 UUID，普通照片）  4=仅视频  5=疑似非原件（体积偏小）

  status        INTEGER NOT NULL,       -- 0=pending 1=copied 2=transcoded 3=done 4=failed
  error         TEXT,                   -- 失败原因，用于诊断报告

  thumb_path    TEXT,
  preview_path  TEXT,

  created_at    INTEGER,
  updated_at    INTEGER,

  UNIQUE(device_id, base_name, taken_at)
);

CREATE INDEX idx_asset_taken_at ON asset(taken_at DESC);
CREATE INDEX idx_asset_kind     ON asset(kind);
CREATE INDEX idx_asset_status   ON asset(status);
CREATE INDEX idx_asset_integrity ON asset(integrity);
```

### 5.3 业务键与去重

- **真重复**（同一文件被导入两次）：业务键 `(device_id, base_name, taken_at)` 命中且 `still_size`/`movie_size` 一致 → **跳过，不重复占用空间**。
- **假重复**（不同文件恰好同名）：业务键不命中（`taken_at` 不同）→ 正常入库；写盘时若目标路径已存在，**加后缀重命名**（`IMG_0001_1.HEIC` + `IMG_0001_1.MOV`，配对关系同步改名）。

### 5.4 索引与真相的关系

**磁盘上的文件是唯一真相，SQLite 只是加速层。** 启动时做一次轻量校验：抽查索引中记录的文件是否存在，不存在则标记为失效条目。不追求强一致。

## 6. 导入管道

三个阶段**流水线重叠**执行，端到端耗时 ≈ `max(传输, 转码)` 而非两者相加。

```
阶段 0  探测（只读，不写任何数据）
  枚举 WPD 设备 → 进 DCIM → 读文件名/大小/拍摄时间
  → 按主名配对 → 与索引比对算出增量
  → 产出任务清单 + 进度总量

阶段 1  传输                                            ┐
  N 个并发 WPD 流读原始字节 → 写盘到 originals\          │ 两阶段
  每写完一个文件，立刻把校验+缩略图任务推给阶段 2          │ 同时进行
                                                        │
阶段 2  校验 + 缩略图 + 索引                             │
  ffmpeg 工作池（CPU 核数 - 1 个并发）                   │
  → 读 ContentIdentifier 做配对校验                     │
  → 从静态图出 thumbs/<hash>.webp                       │
  → 每完成一条就地更新 SQLite                            ┘
```

> **预览片（`previews/`）不在这条管道里生成。** 它由浏览界面悬停触发，见 §7.2。
> 导入阶段只做缩略图，这是"导入快"和"省磁盘"的关键。

### 6.1 状态机与断点续传

`pending → copied → transcoded → done`，失败项标 `failed` 并保留 `error`。

中途拔线、断电、强杀进程都不会留下不一致状态：已 `done` 的绝不重做，`copied` 但未转码的只补转码，`pending` 的重新传。

### 6.2 探测阶段的性能

按 5 万~10 万张规模设计。**仅枚举设备上所有文件的元数据就可能耗时数分钟**，因此阶段 0 必须是可中断、有进度、且结果可缓存的异步操作；第二次插上手机只需比对增量。

### 6.3 并发度

WPD 并发流数量（1 / 2 / 4）需实测确定：iOS 的 PTP 实现可能串行化多个流，此时提高并发反而增加开销。**默认为 1，实测后调整**，作为可配置项。

### 6.4 iCloud「优化 iPhone 储存空间」的拦截

**目标行为**：检测到原件可能不在手机本地时，默认阻止导入，弹出说明与解决步骤（关闭该设置，或改为「下载并保留原件」），并提供一个「我知道风险，强制继续」入口。

理由：静默导入一堆低分辨率副本是最坏的结果，且用户会归咎于工具。

**但检测手段尚未确定**，需实测（候选信号：MTP 报告的已用/可用空间与相册应有总量严重不符、部分文件在资源列表中缺失、属性被标记为云端项）。因此该功能分两步交付：

- **v1 落地**：导入界面提供手动开关「本次的原件可能不在手机上」；导入后对每个条目做体积合理性检查，把明显偏小的标记为 `integrity=5 疑似非原件`，在结果页单独列出。此时**不自动阻止**，只标记。
- **实测通过后**：把手动开关升级为自动检测 + 自动阻止导入。

> 即 v1 交付的是「不骗人」，而不是「自动防住」。这是检测手段未验证情况下的诚实取舍。

> **实测关联（2026-09-17，阶段 3）：** 传输低速的瓶颈被定位为「同一文件**首次访问**约 0.5~10s、
> 第二次约 38 MB/s」，且慢的文件每次不同（状态相关）——属于**设备/驱动侧的首次访问缓存行为**。
> **已排除本节的 iCloud 优化存储**（用户确认未开启），两者不应混为一谈。iCloud 检测仍待实测，
> 但不是低速的原因。详见 `notes/2026-09-17-import-smoke.md`。

## 7. 媒体处理

### 7.1 派生资源

| 资源 | 规格 | 生成时机 | 用途 |
|---|---|---|---|
| 缩略图 | 512px 宽，WebP | 导入时 | 网格视图 |
| 预览片 | 480p，H.264/MP4，约 100~400 KB | **按需**（悬停触发） | 悬停播放 |
| 大图 | 原分辨率，临时解码 | **按需**（点开触发） | 单张查看 |

### 7.2 按需策略

- **预览片不预生成全量**：5 万张全量约 2~3 GB。改为悬停触发、生成后落盘缓存，并配合一个低优先级后台队列预取当前视口附近的条目。
- **大图不落盘**：全尺寸 JPEG 若全量生成将达 100 GB 级。改为点开时临时解码（约 100~300 ms）、走 LRU 内存/临时文件缓存、看完即弃。
- **原片播放**：视频原件是 HEVC，WebView2 不可靠支持，需要时按需转码。

### 7.3 悬停触发的防抖规则

- 悬停停留 **≥ 350 ms** 才触发预览片生成；快速划过不触发
- **滚动中一律不触发**；滚动停止后 300 ms 内也不触发
- **缩放中及缩放结束后 300 ms 内不触发**
- 同时**最多 2 个预览片生成任务**在跑（不抢占界面与传输的 CPU）
- 生成期间显示静态图 + 淡进度指示，可播放后自动淡出

> 这里的 2 个并发与 §6 导入阶段的 ffmpeg 工作池是**两个独立的池**，各自限流，互不抢占：
> 导入池吃 `CPU 核数 - 1`，悬停池固定 2。两者同时活跃时由操作系统调度，实际并发上限是两者之和。

### 7.4 缩略图分辨率与放大上限

缩略图统一 512px。**最大放大档位根据屏幕 DPR 动态限制**，保证任何档位下缩略图都不糊（高分屏上就是少让用户放大几档）。想看得更大就点开单张走按需高清。

理由：网格浏览不需要看清毛孔，那是点开看的事。用一档缩略图 + 可用的按需高清，性价比最高。

## 8. 前端架构与性能

> **实测状态（2026-09-17，阶段 1）：决定 2 与决定 3 已在 `src/components/PhotoGrid.vue` + `src-tauri/src/protocol.rs` 落地并实测通过**（本地图片目录、dev 构建；滚轮与拖动滚动条均流畅）。实测记录与两处必要的实现修正（滚动停稳后再加载图片；协议加 ETag/304）见 `docs/superpowers/notes/2026-09-17-grid-perf.md`。决定 1（唯一 `<video>`）尚未实施，留待计划 4。

### 8.1 三条硬性决定

**决定 1：全局只有一个 `<video>` 元素。**
整个应用保留唯一一个 `<video>`，绝对定位、尺寸跟随悬停的那个格子。鼠标进入格子时移过去、换 `src`、播放；离开时暂停。任何时刻只有一个解码器在工作。

> 反例：一万个格子放一万个 `<video>` 标签，WebView2 会直接崩。

**决定 2：虚拟滚动自己写，不引第三方库。**
网格是**固定尺寸瓦片**，只需算出该渲染哪几行、用绝对定位摆放。通用虚拟滚动库解决的难点（动态高度、测量）在这里不存在，属于白付抽象成本。自己写约 80~150 行。

**决定 3：自定义协议 `lpm://` 供图供片，不走 IPC。**
图片和视频绝不能走 Tauri IPC（要 JSON 序列化，几 MB 的图会卡死）。用自定义 URI 协议绑定磁盘路径，让 WebView2 自己加载，**必须支持 Range 请求**（视频要能拖进度、快速起播）。这样也天然吃到 HTTP 缓存。

### 8.2 缩放

- 拦截 `wheel` 事件（`{ passive: false }` + `preventDefault()`），否则 Chromium 会当成整页缩放
- **离散档位**（如 3 / 5 / 7 / 10 / 14 列），不做连续缩放。最大档位受 §7.4 的 DPR 限制裁剪——高分屏上可能只到 7 列
- **锚点跟随**：缩放前记录光标下格子的序号与相对位置，缩放后调整 `scrollTop` 使其仍在光标下。这是"像 iOS"的关键手感，不做就会每次缩放都跳视图

> 附带收益：Windows 精密触控板的双指捏合也发 Ctrl+滚轮事件，支持这一个功能等于顺带支持了捏合手势。

### 8.3 状态管理

- Pinia 中"当前页照片列表"必须用 `shallowRef`，**不能深响应**。万个对象被 Vue 深层代理，光建 Proxy 就会让切页卡住。
- 前端**不一次性持有全量数据**，靠 SQLite 的 `LIMIT/OFFSET` 分页，内存占用与库规模无关。

## 10. 错误处理与诊断

### 10.1 异常项分类

| integrity | 含义 | 界面表现 |
|---|---|---|
| 0 正常 | 配对完整且 UUID 一致 | 正常 |
| 1 校验不一致 | 文件名配对成功但 UUID 不匹配 | 标黄，可筛选 |
| 2 残缺实况 | 有 UUID 但缺伴生文件 | 标黄，提示"可能需在手机上重新下载" |
| 3 仅静态 | 无 UUID，判定为普通照片 | 正常 |
| 4 仅视频 | 无配对静态图 | 正常 |
| 5 疑似非原件 | 文件体积明显偏小，可能是 iCloud 占位副本 | 标红，单独列出，提示重导（见 §6.4） |

### 10.2 诊断报告导出（开源项目的刚需）

开源后会收到各种机型、各种 iOS 版本的 bug 报告，而维护者拿不到对方的设备。因此**从第一天就要有**"导出诊断报告"功能，输出为一个文本文件：

- 设备型号、序列号（打码）、iOS 版本、WPD 报告的能力集
- 探测到的文件总数、各类异常项计数
- 失败条目的 `error` 原文（ffmpeg stderr、WPD HRESULT）
- 运行环境：Windows 版本、ffmpeg 版本

**绝不包含任何照片内容或文件名以外的元数据。**

### 10.3 删除语义

- 删除 = **移到 Windows 回收站**（可后悔）
- 删除实况照片的其中一半时，提示"这会破坏实况配对，是否两个一起删"
- 已知限制：回收站有容量配额，超出配额的大视频会被永久删除；大批量删除走 shell 操作较慢

## 11. 分发与构建

- **分发形态：绿色版（免安装）优先。** 用户解压即用、免管理员、不写注册表。Tauri 官方**没有** portable 打包目标，实现方式是 `tauri build --no-bundle` 后手工组装 zip：裸 `exe` + 同目录兄弟 DLL（含 `WebView2Loader.dll`）+ `resources/`（与 NSIS 安装包落地的布局一致）。**不支持单文件 exe**（WebView2 加载器与资源需同目录）。可另外提供 NSIS 安装包作为可选项。**落地细节写入后续的打包计划。**
- **WebView2 运行时**：Win10/11 一般自带；缺失时会白屏，绿色版不捆绑 bootstrapper（否则就变成需要安装动作），改为在 README / 首次引导中提供说明。
- **未签名会被 SmartScreen 拦**：首次运行需"更多信息 → 仍要运行"。这是绿色版首发体验的主要痛点。
- **许可证：待定**（倾向 GPL-3.0；见附录 A）
- **ffmpeg**：使用裁剪版静态构建，只保留 HEIC 解码 + HEVC 解码 + H.264 编码 + 必要 muxer，目标体积 15~25 MB（完整构建约 80 MB，对"轻量软件"定位过重）。作为 sidecar 放入 zip 的 `resources/`，运行时用 `BaseDirectory::Resource` 解析。
- **代码签名**：是否购买代码签名证书待定，不影响架构，只影响首次运行体验
- **发布渠道**：GitHub Releases
- **纯净性**：库数据全部在用户指定的库目录内（`.lpm/` 随库），不依赖任何系统级写入。后续若引入会写 `%APPDATA%` 的插件（如窗口状态），需改为写到 exe 同目录或干脆不用。

## 12. 风险登记

| 风险 | 等级 | 应对 |
|---|---|---|
| MTP 不暴露实况照片的 `.MOV` | **致命** | **阶段 0 探测程序先行验证**；若不成立需重新评估通道（本地备份解析 / iCloud API） |
| 无法可靠检测「优化 iPhone 储存空间」 | 高 | 检测手段实测确定；保底方案是手动强制继续入口 + 导入后标记疑似项 |
| iPhone 走 WPD 的怪癖（需先信任电脑、会话行为与 Android 不同） | 高 | 不依赖 `mtp-rs` 等第三方封装（其官方仅验证过 Android），直接用官方 `windows` crate 的 WPD COM 绑定，行为可控、可调试。**已实测证实并给出对策，见下一行** |
| **iOS 对象句柄易失 → 取流会拿到"错误对象"的数据** | **高（实测新增，已修复）** | 阶段 3 实测：直接拿枚举得到的句柄 `GetStream`，会**静默写入错位的内容**（无报错）。修复：枚举时存 `WPD_OBJECT_PERSISTENT_UNIQUE_ID`，传输前用 `GetObjectIDsFromPersistentUniqueIDs` 重解析新鲜句柄。教训：传输必须校验字节数，不能只看有无异常。详见 `docs/superpowers/notes/2026-09-17-import-smoke.md` |
| **视频（MOV）的 `GetStream` 仍偶发失败；会话被强杀会卡死** | 高（实测新增） | 干净会话下用退避重试兜住（`0x80042007` / `0x8007001E`）；会话卡死只能物理拔插恢复——产品需加入"会话失效请重插"引导 |
| ffmpeg 裁剪构建的兼容性 | 中 | 先跑通完整构建，再裁剪 |
| WPD 并发流无收益 | 中 | **已实测（阶段 3）：并发无收益且引入 `ERROR_BUSY`**。2 线程 2.09 MB/s 但 10% 失败，4 线程反降至 1.42 MB/s、失败率 33%。**维持并发 = 1** |
| **传输速率偏低，且瓶颈是"文件首次访问"的设备端延迟** | 中（实测新增） | 阶段 3 定位：**首次读取约 0.5~10s（≈1 MB/s），第二次读取约 38 MB/s**；解析/握手/收尾均非瓶颈，并发无收益。慢的文件每次不同（状态相关）。**已排除 iCloud 优化存储**（用户确认未开启）。机制从主机侧无法进一步区分。整机耗时下限 ≈ Σ(每文件首访延迟)。详见 `notes/2026-09-17-import-smoke.md` |
| 大批量导入耗时长（10 万文件枚举需数分钟） | 中 | 阶段 0 异步化 + 结果缓存 + 进度可见 |
